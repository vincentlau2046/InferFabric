# 双机协同约定（vince-pc ⇄ Mac）

状态：2026-11-24 用户裁决（方案 A · 轻约定；交替使用形态）；2026-11-25 按用户要求补记
跨端 PR 开工握手、验证分级和合并签收规则。本文件是两端 Claude session 的开工/收工执行清单，修改须经用户确认。

## 1. 角色与拓扑

- 唯一共享枢纽：`origin = github.com/vincentlau2046/InferFabric`。两端地位对称，
  **交替使用**：同一时间只有一端在开发，换机即交接。
- vince-pc：Linux + RTX 5090D，生产 :8999（NInfer/vLLM/SGLang 路线）；代码改动沿用
  sandbox-first（见 constitution.md）。
- Mac：darwin-arm，生产 :8999（launchd `com.macfabric.gateway`，llama.cpp/Metal +
  packs 路线）；feature-branch + PR 直做（已实践：PR #37/#38/#39）。
- 机器私有状态永不入库：`.state.db`、`_deps/`、`sandbox/`、`~/.inferfabric`、日志
  （.gitignore 已覆盖，勿加白名单）。

## 2. 交接协议（核心，交替形态下每次换机都走一遍）

**收工（一端停止开发时）—— 五件事：**
1. push 所有 WIP 分支（没写完也推，标题标 `WIP:` 或开 draft PR）；
2. 计划/spec/STATUS 等文档随代码入库，不留 untracked；
3. 更新对应 `specs/*/STATUS.md` 当前行（做了什么 / 停在哪 / 下一步）；
4. 未完成事项开 issue 或在既有 issue 留言，写明交接说明；
5. 不留"只有本地知道"的分支——本地分支要么已推远端、要么已合并删除。

**开工（另一端接手时）—— 四件事：**
1. `git fetch --prune` → 切 main → pull 对齐（**绝不基于旧 main 开新分支**）；
2. 查远端分支 + issues + 相关 STATUS.md，确认对端停在哪、有无 WIP 可续；
3. 新任务从最新 main 开新分支；续作则 checkout 对端推上来的分支；
4. 跑受影响模块的 unit+integration 冒烟，确认基线绿再动手。

## 3. 集成与分支卫生

- 一切进 main 走 PR（docs 也走 PR，成本就是自己点 merge，换来历史干净、对端可见）；
- 合并即删远端分支；存量 `pick/*` 与已合并分支做一次清理归档；
- commit message 沿用 conventional commits（feat/fix/docs/chore + scope）；
- **版本迭代（2026-11-24 用户裁定）**：patch 位（`0.0.x` 的 x）由任一端 Claude 自主升级，**每轮修改迭代一个 patch**（合并前自升 + README 版本历史表加行）；minor / major 须经用户裁决。版本位置：`inferfabric/__init__.py` + README 版本历史表。

## 4. 评审与验证

### 4.1 验证分级（按变更影响，不按机器名字）

- 代码 PR 保留 constitution 的 LLM cross-review（GLM-5.2）和双端 unit + integration 基线。无 CI（方案 A 不加 Actions）；最后 push 的主责端负责收齐证据与全量绿，不能代签另一端结果。
- **仅文档或纯视觉**：文档验证链接与 diff；纯视觉代码按现有代码回归要求，加受影响页面冒烟，不因跑在 Ubuntu 就占用 GPU。若实际改变状态、端点或平台文案含义，按共用功能验。
- **共用网关／UI／配置契约**：Mac（Apple Silicon）与 Ubuntu（x86 + NVIDIA）各自在隔离实例做受影响的功能验收。能模拟就不消耗真机时段，例如云端接入、路由与别名用模拟上游；约定中的另一端可选代码复审，不能代替必需的跨端验收。
- **硬件或平台专属行为**：涉及引擎生命周期、平台探测、进程收割、显存／统一内存准入、硬件运行时或依赖本地状态的路由时，逐项列明受影响平台和必测场景。NVIDIA GPU operational 只在 vince-pc 或另行约定的 Ubuntu 验证主机跑；Apple Silicon 用其独立代表路径。只认实测组合：列出 Ubuntu 版本、x86 架构、驱动、GPU 和引擎版本，某一组合通过不代表其他组合。

### 4.2 开工握手与写入权

1. **主责端发起 Draft PR**：链接 spec，写明目标／不做什么、共用契约、拟主写端、两端用例、必验平台与预计窗口。涉及 Ubuntu 验证的 PR 在描述或点名评论中 `@` 实际接收通知的 GitHub 账号；不使用猜测的用户名。若接收路径未确认，先落实接收人及如何转给 Ubuntu agent，再发通知。GitHub `@` 只是通知，不等于 agent 在线或已接单。
2. **两端显式回执**：主责端确认负责范围，另一端确认接手验收范围、环境与窗口，或回 `受阻` 并写明缺项。通过 PR 保留回执；若口头或其他消息渠道先确认，把双方结论回填 PR。未回执记 `待接手`，只可继续只读调研或完善方案，不启动约定范围内的共享实现。双方先解决契约分歧再开工。
3. **单端主写**：另一端可并行读设计、评审和独立验收，不同时写同一分支；若要换主写方，沿用 §2 开工／收工清单，在 PR 留下接手确认、分支与 SHA、未完成项及下一步。需要改范围或必验矩阵时双方重新确认。

### 4.3 合并签收与真机安全

- 双端分别在 PR 留下：`平台／环境 | 所测 commit SHA | 用例或命令 | 通过／失败／受阻／未跑（及原因） | 脱敏证据`。若一项确实不适用，在开工握手时明确理由。真实硬件结果同时记录实际服务／引擎版本、是否恢复起始状态；私有配置、凭证和原始日志不入库。
- 功能 PR 的必验项均通过、双方签收且其他既有门禁满足才可合并。PR head 更新后，受影响用例必须在新 SHA 上重验；未受影响的签收可由验收方核对 diff 后在 PR 明确确认继承并注明原／新 SHA。若更新基线使实际合并内容改变相关行为，同样重验。窗口未获准、设备不可用或结果失败就保留阻塞，不能用 Mac、mock 或一台 GPU 的结果替代另一必验项。
- 真机前由主责端申请窗口和影响面许可；验证端核对脚本、隔离数据目录、测试网关地址及其身份、GPU／内存占用、重要任务、清理和回退路径。现有 operational 用例默认可能指向 `:8999`，不能盲跑，不默认触碰生产。运行中观察真实终态（例如实际推理结果、进程退出、资源归还）并约定中止条件；失败先停、恢复、再回填证据。开工回执不等于生产操作授权。
