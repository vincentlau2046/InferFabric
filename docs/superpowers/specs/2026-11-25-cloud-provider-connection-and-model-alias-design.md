# 云提供方接入：原地编辑与模型调用别名

- 日期：2026-11-25
- 状态：用户已确认产品范围；本文是待审设计，不是实施授权。尚未双端握手、开实现 PR 或运行验收。
- 优先级：P0 存量加固；不依赖控制台整体重排。
- 协同规则：[双机协同约定 §4](../../../steering/dual-machine-collaboration.md#4-评审与验证)。

## 1. 目标与取舍

个人工作台的常用维护应该在界面完成。现在已添加的云提供方有测试、发现、模型管理和删除，但没有原地编辑；为了换凭证或端点删了重加，会让模型与池引用承受不必要的变更。不同提供方的同名模型也不能只凭模型名稳定区分：注册表有裸名和提供方限定名，旧裸名按既有规则解析；模型列表存在按短名折叠的路径。

| 方案 | 取舍 |
|---|---|
| 只补换 Key，或只给模型加显示名 | 改动最小；解决不了端点维护与精确调用，显示名不会决定实际去向。 |
| **原地编辑提供方 + 显式单目标别名 + 保留旧调用** | **已选。** 稳定提供方 ID 与现有绑定；用户可以安全换连接，也可以精确选定同名模型的实际上游。 |
| 改写所有裸名规则，或直接引入多账号／每模型独立 Key | 会牵连存量调用与凭证归属；没有当前使用需求，不做。 |

不做账号池、每模型凭证、自动跨厂商回退、默认路由迁移、广泛 UI 换肤、远程管理或新的平台运行时。沿用本机控制台的现有管理边界，不增加日常登录门槛。遵守 [constitution](../../../steering/constitution.md) 的转发核心边界：优先在管理面和目标解析层完成，复用既有转发；如不能在边界内落实，暂停并提请裁决，不借别名重写转发链。

## 2. PR 1：原地编辑连接

- 提供方行增加「编辑连接」。常用项：显示名、上游 API Key、OpenAI／Anthropic 地址、启停。高级项：现有发现设置和超时。提供方 ID 不变；显示名不是路由名。已启用／手填模型、池引用与顺序、下游客户端配置不因编辑而重建。关闭提供方或修改协议地址前，显示受影响的模型与池；关闭后不能继续选用该提供方，池按原有策略处理不可用候选。
- 交互：**编辑 → 测试拟变更的连接 → 确认应用**。更换 Key 或地址时，测试与要应用的配置版本绑定；继续修改就需重测。若只测了通路，显示「连接通过，模型未验证」；实际推理探针则标出模型和协议。普通显示名编辑不要求联网测试；已停用连接不会因编辑而自动启用。
- Key 空白表示保留；外部环境托管的凭证标注来源、不可在 UI 覆盖。编辑换域时显示新目的地，首次向新域探测前必须显式输入该域要用的新 Key，或显式选择不带凭证；**不把已存旧 Key 自动发送到新域**。上游提供方凭证与发给客户端的网关 API Key 分开命名、分开管理。任何读接口、预览、错误及日志不得返回 Key 明文。
- `cloud_provider.yaml` 是非敏感连接字段与凭证引用的配置源，凭证值只入凭证存储。UI 与手改 YAML 共用配置和校验，只持久化目标字段，保留存量其他字段与模型配置。不从运行中展开过的 Key 反写外部来源。应用按配置版本防覆盖；遇到外部文件修改、其他编辑或发现任务竞态，不以旧视图覆盖新设置。预览可显示脱敏差异。
- **应用成功以持久化和运行态都成功为准。** 测试失败不写配置；应用失败保留原有效连接和可重启的原配置；不留半套新配置。变更成功后新请求使用新设置，已在途请求无需强切，重启后仍一致。已有 `secrets.env` 注入使用 `setdefault`，不能把「改了文件并 reload」当作已换 Key；实施方需明确受管与外部来源优先级，并以两种不同测试凭证观测实际出站值。旧发现任务的结果不得覆盖新版本或让停用项目复活。

**评审后补记的首版建议（待本文确认）**：

- 一个连接仍只用一把上游 Key。若只更换其中一个协议的地址，不产生「一个端点有 Key、另一个端点无 Key」的隐含配置。拟用同一把 Key 或无 Key 的方案须适用于该连接下受影响、仍启用的所有协议，否则保留旧配置。更换 Key 或地址的最小放行证据是相应协议的一次已验证鉴权或最小真实调用；公共 `/models` 的 200 只能算连通，不能当作鉴权通过。无合适探针时显示未验证，首版不提供「跳过测试并激活」。
- 对已管理的连接，旧凭证只能发给已确认的目的地（协议、主机、端口）；配置重载、重启和探针重定向都不能绕过目的地限制。手改 YAML 新增目的地时，必须一并显式声明凭证与新目的地的绑定，不把改 URL 本身当确认；没有确认时不激活冲突改动。兼容存量未修改的连接。存量 YAML 内联 Key 不做全量自动迁移；编辑该连接并成功应用时，才将该连接的内联 Key 转为凭证引用，失败保旧。

完成标准：不用改 YAML 或删厂商，就能换 Key／地址；现有模型与池绑定不变；错误 Key、配置冲突和保存失败均可理解且不破坏原连接。

## 3. PR 2：同名模型与调用别名

来源身份是稳定的 `(provider_id, upstream_model_id)`。云模型列表按此身份显示，不因另一家提供方有同名模型而隐藏一行；保留上游的完整 ID（可能含 `/`）。已启用、可路由的云模型行可设置一个可选的调用别名，并复制它作为客户端的 `model`。池候选仍指向来源身份，不改成引用别名。

| 场景 | 行为 |
|---|---|
| A 与 B 都提供 `glm-5` | 列表显示两条来源，可分别给 `glm-5-a` 和 `glm-5-b`。 |
| 调用 `glm-5-b` | 精确解析到 B 的 `glm-5`；上游请求用原始 ID，而非别名。沿用对应协议的鉴权与转发，不增加协议能力。请求记录保留既有实际目标归属。 |
| B 停用、模型撤销或协议不支持 | 已声明的别名不能掉回裸名、另一提供方、模型池或本地模型；在目标解析或上游错误处明确失败。不可调用的别名不宣称可用。 |
| 旧客户端继续用裸名或既有显式名 | 保留现有解析行为，不改默认去向、不强制迁移。撞名在 UI 提示并建议使用显式调用名。 |
| 修改或移除别名 | 提示旧调用名会受影响；不影响对应上游身份或池候选。 |

别名不是模型显示名，也不是回退池。别名应和本地调用名、云旧调用名、其他别名、模型池名称及保留命名空间隔离，冲突拒绝且不写入；后续配置载入或发现不能静默夺走已使用的调用名。`/v1/models` 公布当前可调用的显式别名且无重复 ID。别名是 YAML 中的显式意图（绑定来源身份、无凭证），配置文件重载或重启后仍存在；发现只刷新候选和元数据，不替用户改别名，不改变既有[云模型保留规则](../../../specs/pr26-cloud-registry-floor/spec.md)。具体字段、命名校验和解析位置由实施方案定，但不得改变上述兼容契约。

**评审后补记的首版建议（待本文确认）**：

- 不改既有网关鉴权策略；在要求鉴权的入口，新增别名不继承上游模型或池的受限 Key 权限，首版不提供给受限 Key 单独授予别名的入口。验证旧调用权限不变，且受限 Key 不能借别名扩大权限。
- UI 或热加载引入冲突时不应用冲突更新，保留在役配置并报出冲突项；冷启动没有在役快照可保时，冲突的调用名明确报错，不公布为可调用，其他不冲突的模型正常工作。禁用与删除不同：禁用连接或撤销模型时保留别名绑定，目标显式恢复后可继续用；删除连接后别名保留为未激活，重建同名连接不得自动复活旧别名，须显式确认恢复或移除。

## 4. 双端验收与交接

两项是共用网关／配置行为，不是硬件功能。**两个 Draft PR 都需写明 Mac 与 Ubuntu（x86 + NVIDIA）责任端和验收项，`@` 实际 Ubuntu 接收账号，双端确认后开工；接收账号与回执路径待正式开 PR 前确认，不在本文假定。** 单端主写，另一端评审和在自己的隔离环境独立验收；正式交接才换主写方。以下共同用例两端各执行，并按 [协同约定](../../../steering/dual-machine-collaboration.md#42-开工握手与写入权)回填所测 SHA 与结果。

| 验收 | PR 1：原地编辑 | PR 2：模型别名 |
|---|---|---|
| 有效行为 | 用模拟上游记录到达的端点和测试凭证，确认换 Key／换地址后**新请求**生效，重启后读回一致；显示名、现有模型与池绑定不漂移。 | 两个隔离模拟上游都提供同名模型；在各支持的协议验证实际命中的上游、凭证与上游收到的原始 ID，包括含 `/` 的 ID；`/v1/models` 可发现已启用别名。覆盖 OpenAI Chat、Anthropic Messages 及现有可用的 Responses 路径，按目标能力断言，不顺带新增协议支持。 |
| 失败与兼容 | 错 Key、公开连接探针误报、写入失败、并发文件变化、外部托管、换域或重定向不泄漏旧 Key、旧发现任务不覆盖新配置；停用后旧连接不可被后台任务复活。 | 撞名拒绝，不覆盖本地／旧云名／池；停用或不支持协议时不串路由，删除再添加不自动激活别名；受限 Key 权限不扩大；重载、重启和再次发现不丢绑定；旧裸名、旧提供方限定名和已有池行为不变。 |
| UI 与常规回归 | 两端走查编辑、测试结果和影响提示；检查网关基本端点、全量 unit + integration、导入与受影响运行冒烟。 | 两端走查同名两行、复制别名、冲突反馈；同样检查全量 unit + integration、导入与受影响运行冒烟。 |

只用测试凭证、隔离数据目录和非生产网关；不在验收记录中贴 Key、原始请求或私有日志。**两项基线均不需要占用 NVIDIA 真机。** 如果范围扩到本地生命周期、NVIDIA 路径、资源准入或本地池就绪，先重新划定范围，并在 PR 列出必验 Ubuntu／驱动／GPU 组合和获准窗口，未验的必验项阻塞合并。

## 5. 实施边界

先评审并确认本文与通用规则，再排实施计划、确认两端接收人并发 Draft PR。PR 1 与 PR 2 分别验证、评审和放行，不与控制台大重排捆绑。API 方法、事务与锁实现、别名配置的具体字段以及测试脚本组织留给实施计划；不得以简化实现为由放宽凭证保密、失败保旧、精确路由和存量兼容四项契约。
