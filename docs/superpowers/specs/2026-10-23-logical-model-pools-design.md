# IFF 逻辑模型池与双协议路由设计

日期：2026-10-23
状态：待用户审阅的完整设计；不是已实现功能，也不是生产部署授权。

## 1. 目标与已知约束

用户需求：为多 agent 提供 fast、premium、small、classifier 四个稳定的逻辑模型名；可以实时修改真实模型映射，每个槽位允许多个候选、优先级和槽位内自动切换；同时正确支持 OpenAI 与 Anthropic（ant）协议。

目标是让客户端配置稳定、后端选择可控、故障可解释，不把客户端协议、模型身份与GPU进程切换混为一谈。

约束：

- IFF 是单卡 Blackwell 工作站的有状态网关，已有 :8999 双协议入口。
- 开发与测试均在 sandbox；不升级 vLLM/驱动/NInfer，不启用或修改 sleep/wake。
- 当前并发协调修复独立推进；新路由不能冒充已经完成的稳定性补丁。
- PR-14 冻结转发核心：真正的候选故障回退需要独立 spec 与明确的最小变更授权，不能宣称仅改 YAML 即可实现。
- 本文默认跨本地/云回退关闭、跨协议转换关闭；这两点是设计者的保守建议，不是用户已经拍板的要求。

## 2. 结论：入口端口固定，客户端协议固定

外部仍使用 IFF 8999 端口或其既有安全入口，不因所选模型变化而改客户端端口。

| 客户端协议 | 请求端点 | 常见 SDK base URL 写法 | 请求 model |
|---|---|---|---|
| OpenAI Chat Completions | POST /v1/chat/completions | http://IFF主机:8999/v1 | iff/fast 等 |
| Anthropic Messages | POST /v1/messages | http://IFF主机:8999 | iff/fast 等 |

具体 SDK 是否自己追加 /v1 必须在接入页按客户端验证，避免 /v1/v1。用户的客户端继续使用原来的协议与认证方式；OpenAI 请求不会因为换成另一个模型就改走 /v1/messages。

本期的 openai_chat 特指 Chat Completions，不把 /v1/responses、旧 Completions、Ollama 原生协议或 embeddings 混为同一类协议。当前既有直连路由是否提供这些端点，不等于本设计自动保证其池化兼容。

上游引擎可以各用不同端口，云端也可以有不同 Base URL；这些变化由 IFF 后端目标注册信息承接，客户端不感知。

前提：调用端支持指定 model 名称。若某工具硬编码模型名或没有独立 classifier 配置，仍需一次性修改该工具配置；不能保证 IFF 单方面接管所有第三方工具的内部模型选择。

## 3. 六个独立概念

1. **逻辑槽位 Pool**：iff/fast、iff/premium、iff/small、iff/classifier；允许以后新增自定义槽位，不写死只能四个。
2. **真实目标 Target**：某个本地 ModelConfig，或明确 provider + 上游 model_id 的云模型。
3. **协议端点 Endpoint**：目标对某种协议可用的接入点，含 protocol、URL来源、该协议的上游模型ID、认证来源、能力和验证状态。
4. **选择策略 Policy**：优先级、候选启用状态、位置边界、故障回退、总尝试次数和总耗时。
5. **就绪/健康 State**：本地是否ready、端点故障冷却、限额、半开探测。状态不等于配置，也不等于“Provider URL可达”。
6. **GPU生命周期 Lifecycle**：引擎加载、停止与独占资源分配。池路由不能自行发明一套进程管理逻辑。

一个真实目标可以出现在多个池中，但这不意味着启四份模型实例；同一目标的并发容量需要共享核算。

候选应使用结构化引用，不能依赖 split('/')[-1] 推断身份：云模型真实 ID 本身可以含 /，并且不同 provider 可能有同名模型。保留 iff/ 前缀作为逻辑池命名空间，配置加载时拒绝冲突。第一版禁止池引用池，避免递归/循环。

## 4. 双协议如何选择和切换

### 4.1 一张逻辑映射，两条兼容候选视图

每个池维护一张候选列表。每次请求按入站协议与功能要求过滤，再按优先级选择。面板分别展示“OpenAI 有效候选”和“Anthropic 有效候选”，不要求用户维护两份池配置。

| 目标端点能力 | OpenAI 入站 | Anthropic 入站 |
|---|---|---|
| 仅 openai_chat | 可选 | 不可选 |
| 仅 anthropic_messages | 不可选 | 可选 |
| 两种都已验证 | 选其 openai_chat 端点 | 选其 anthropic_messages 端点 |
| 支持范围未知/未验证 | 不默认当作兼容 | 不默认当作兼容 |

因此，同一个 iff/fast 可以在两种客户端中选择不同的真实目标。槽位表示服务档位，不承诺跨协议一定是同一模型实例；如业务需要同一模型，应配置一个双协议已验证目标，或为该池要求双协议覆盖。

优先级与可用性按请求协议解释：同一云Provider的 OpenAI 端点失败，不应直接把其 Anthropic 端点判死；共享凭证失效等跨端点故障可提升到Provider层。

### 4.2 第一阶段不做跨协议转换

OpenAI JSON不能只换URL就发给Anthropic；反向同理。消息结构、system、工具定义、tool_result、停止原因、流式事件、usage、思考块均可能不同。

第一阶段只做“同协议请求→同协议端点”的原生转发。没有兼容候选就明确报错，不静默转换、不丢字段。

### 4.3 可选转换层是独立阶段

以后确有需求，可以评估自建受控 adapter，或固定版本的 LiteLLM 等工具；必须验证请求与响应两向转换、工具调用、流式、usage和错误契约。

转换可以有损，必须显式启用，并列出不支持的特性。签名思考块、provider绑定状态、加密推理状态等不可承诺通用无损转换；不能因模型都支持“文本”就认为任意agent对话可以迁移。

转换依赖工具的当前版本、许可证和社区/企业能力边界尚未核验，本设计不作产品功能保证。

## 5. 候选配置与来源

新增独立机器配置 model_pools.yaml，不复用当前无消费端的 model_affinity.yaml。Provider URL/密钥仍由现有 Provider 配置管理，本地模型仍由 models.d 管理，模型池只引用它们，不复制保存凭证或启动参数。

结构示意（非现有配置语法，示例Provider/模型均非现役绑定）：

```yaml
schema_version: 1
pools:
  fast:
    enabled: true
    strategy: priority_failover
    allowed_locations: [cloud]
    allow_protocol_translation: false
    local_activation: ready_only
    max_attempts: 2
    deadline_ms: 60000
    candidates:
      - id: fast_primary
        priority: 10
        target:
          kind: cloud
          provider: provider_a
          model_id: model_a
      - id: fast_backup
        priority: 20
        target:
          kind: cloud
          provider: provider_b
          model_id: model_b
```

数值用于解释结构，不是性能标定后的生产默认值。premium/small/classifier 使用相同结构；未配置候选的槽位保持禁用，不假装可用。

本地候选使用 kind:local + model_name，不含端口、Docker命令或任意URL。上游协议与模型ID的关联由TargetEndpoint提供，必要时可为不同协议配置不同上游ID，不能假定两个协议总是使用同一model_id。

当前 CloudModel.openai_available/anthropic_available 与 ProviderConfig.openai_base/anthropic_base 可作为元数据起点，但“填了base”不足以证明该模型、该协议和该功能已可用。需要校验/探测状态，且探测不默认触发真实本地模型启动或付费生成。

优先级数字越小越优先；第一版不做权重随机、轮询、语义分类或自动改排序。重复candidate ID、重复优先级、悬空目标和协议覆盖不足应在保存时说明/拒绝；候选健康变化不改写配置。

### 5.1 兼容性证据契约

以下是本设计选取的保守规则，不是已实现机制：

- 证据按“目标+协议端点指纹+上游模型ID+具体功能”保存，区分 unknown（未知）、declared（管理员明确声明）、probed（对应行为用例通过）、failed（验证失败）、stale（依赖变化后失效）。普通文本生成成功不证明 tools、stream、图像或结构化输出都可用。
- 发现列表和现有 available 标志只提供待核验元数据；列表探测成功不升级为生成协议或高级功能的 probed。
- 默认只接受对应协议及本请求必要功能的有效 probed 证据。允许管理员逐端点、逐功能显式启用“接受声明”，此时 declared 可参与选择，但面板标为“管理员声明，未经行为测试”，不能冒充已实测。unknown/failed/stale 不参与选择；新声明不能悄悄覆盖已知失败，需显式清除失败并记录管理员操作。
- 静态 validate 与 dry-run 不发生成请求。实际协议/功能验证只能由管理员明确启动，列出目标、用例、是否出站及可能费用；本地启动、GPU切换、VL使用限制仍单独生效。探测仅用合成测试数据，不重放真实用户历史。
- 证据记录时间、来源/操作者、用例版本及依赖指纹。端点URL、认证版本、协议上游ID或能力相关部署配置变化后，相应证据变 stale，必须重新验证或明确重新声明；不能沿用旧地址的成功结论。

## 6. 请求选择与安全回退

### 6.1 确定性选择顺序

1. 从请求路径确定协议，识别 iff/ 逻辑槽位；非逻辑名继续既有直连路径。
2. 校验身份、池权限、目标范围及数据出站边界。
3. 捕获一个不可变路由快照与revision；本请求始终使用它。
4. 提取本次必要能力：stream、tools、输入模态、结构化输出、上下文与输出上限等。
5. 过滤禁用、不兼容、未就绪、冷却中或超出调用方权限的端点。
6. 若会话固定到某目标，先按会话迁移规则处理；否则按优先级选择。
7. 在统一尝试预算与deadline内执行，输出开始前按明确规则回退。
8. 按入站协议返回成功/错误，并落请求与attempt日志。

上下文估算要承认不同tokenizer差异；不得为适配备选模型偷偷截断对话或删除tools。未知能力不能默认当成支持。

### 6.2 哪些错误允许切下一候选

第一版固定动作表如下；“可配置”仅指在表格允许的范围内调整次数/预算/开关，不能把“不回退”类别改成回退。

| 错误类别 | 动作 |
|---|---|
| 连接失败/DNS/端点暂时不可达 | 立即切下一候选（受max_attempts/deadline） |
| 429 / Retry-After 可接受 | 等待受限时间后重试原目标，预算耗尽切下一候选 |
| 5xx（响应头未提交、读取前失败） | 最多重试原目标1次，之后切下一候选 |
| 5xx（已开始输出后失败） | 不重试不切换，按协议截断并记录truncated |
| 上游401/403（凭证错误） | 不重试原目标、该端点进入冷却、切下一候选 |
| 上游404 模型不存在 | 不回退；隔离端点并按配置问题上报 |
| 400/422/内容安全拒绝/能力不匹配 | 不回退，按入站协议返回明确错误 |
| 上下文/输出超限（确定性） | 不回退，返回明确错误 |
| 客户端401/403/未知池 | 不进入选择流程，直接拒绝 |
| 本地not_ready/switching | 跳过本地候选；是否允许跨位置回退由显式策略决定 |

默认不回退的类别不可通过配置放开：客户端身份/权限失败、无效请求、未知池、功能不支持、确定性上下文超限、内容安全拒绝、上游模型配置404。上游凭证错误单独处理：失败端点冷却并切下一候选，但对客户端仍是一次请求、一份按协议的明确结果。

具体状态到动作的映射是明确表格，不能对所有异常一律重试。

### 6.3 统一重试预算，禁止倍增

max_attempts计所有真实上游POST，包含同目标重试，不能外层2个候选×既有内层3次变成6次请求。deadline覆盖排队、连接、等待、退避与读取，并允许分别设置连接/读空闲上限。

因此需要single-attempt传输边界或让现有forwarder接收本请求剩余预算，不能仅在现有forwarder外再套for循环。慢/超时请求可能已被上游处理，切备选也可能产生重复生成计费；不承诺跨模型exactly-once，不对不支持幂等的上游伪造幂等保证。

### 6.4 响应提交后禁止切换

对外成功响应头已经提交，或任何内容/工具事件已经输出后，本次请求不再重发或切换模型。截断应使用协议允许的错误事件或关闭流，并记录truncated，不拼接第二个模型的答案，不在同一已提交响应中再写另一份HTTP/JSON信封。

目标尝试的错误在决定是否回退之前不能先写给客户端。现有forwarder多处分支直接send_json/stream，这是实施时必须显式处理的边界，不是假装已经具备的能力。

### 6.5 熔断与恢复

以“目标端点+协议+配置版本”为主要状态键；只按故障类别计数。OPEN期间跳过，冷却后单飞HALF_OPEN，成功后恢复。无会话绑定的新请求可恢复使用最高优先级目标，已固定的会话不因优先级恢复而强行迁移。

逻辑池内部的重试/熔断不调用classifier模型，防止调度依赖自身形成循环。

## 7. 多agent会话与不可迁移内容

“同协议”不等于任意历史都可跨Provider重放。

- 普通文本、无Provider绑定状态的请求可在显式边界内回退。
- 含签名/加密思考块、Provider私有状态、不可迁移引用等请求，固定目标或失败，不删除这些字段来凑兼容。目标归属按请求内字段判定：Anthropic thinking签名块绑定model，按其绑定模型限定候选；tool_use/tool_result 多轮历史按产生这些往返的当前请求上下文推断，在P1/P2无会话能力时**无法确定原目标即拒绝迁移**（no_compatible_target），不允许“按池内最高优先级猜测”。客户端可在请求内显式声明目标归属（如指定原模型ID）来解锁迁移；会话固定（P3）提供更可靠的归属来源。
- 工具定义能力和多轮tool_use/tool_result历史分别验证。第一版对已有工具往返历史采取保守迁移策略，不声称所有agent历史可跨模型无损兼容。
- 可选 X-IFF-Session-ID 帮助固定真实目标。客户端不提供时不得假装有可靠会话ID，不能仅按API key把所有agent混成一个会话。
- 会话状态按“调用方身份+会话ID+逻辑池+协议”隔离，有TTL/容量上限。候选被配置删除/停用或权限撤销时，不继续以会话粘性绕过规则。
- 热配置对新请求生效；有会话粘性的后续请求按允许候选范围继续固定目标。管理员可显式结束绑定，不能以“实时生效”为由迁移已经进行中的响应。

第一阶段不要求改客户端协议/端口；需要可靠会话粘性时，接入工具可能需要额外配置一个会话header，这是可选能力而非无条件零配置承诺。

## 8. 本地GPU与云端的数据/费用边界

默认 local_activation:ready_only：池选择不自动卸载或抢占当前本地模型，也不自动启动VL。未就绪本地候选跳过或报not_ready。

可选未来策略 start_if_idle 必须走唯一生命周期入口、持锁、同目标单飞、等待ready；不能从池路由直接操作容器/进程。抢占另一独占模型不属于第一版。

不同池指向同一本地目标时共用容量门；classifier的短请求不能因此被承诺一定与premium有物理资源隔离，需要结合执行资源/队列隔离单独验证。

本地→云、云→本地、云Provider之间的切换均受显式候选列表与allowed_locations/出站策略约束。未配置的Provider不能成为备选。跨本地/云默认关闭，用户若批准可以逐池开启。

云回退涉及费用和数据位置；未知价格不当作免费。第一版做明确候选/出站限制和用量归属，不宣称具备严格的多租户预算硬顶；预算若后续加入，还需并发预留与未知usage处理。

## 9. 权限、日志与缓存

### 9.1 权限

保留现有主key/guest能力，扩展为显式池授权与可选目标/出站限制。

- 旧guest模型白名单不会因新增逻辑池自动获得更多模型权限。
- 授权某池意味着允许管理员配置范围内的服务选择；若调用方有更严格allowed_targets/出站约束，实际候选仍须满足这些约束。
- 若策略要求同时授权池和目标，就在每次选择时做交集检查，不能只检查短名 fast。
- 目标必须使用限定身份，不能按最后一段模型名跨Provider放行。
- 管理配置接口复用管理认证，但不因此公开整个管理面；外部安全入口仍只放行必要数据面。

### 9.2 日志与指标

请求级：request_id、logical_model、最终target、入站/上游协议、revision、session绑定状态、最终结果、总延迟、usage。

attempt级：attempt序号、target、失败阶段/原因、耗时、是否已提交响应、回退原因。统计分别展示“客户端最终成功率”和“上游attempt失败率”，防止备用成功掩盖主端点持续故障。

费用归属于实际目标，不能按逻辑名估一个固定价格。诊断信息默认在受保护接口可见，不向所有客户端泄漏内部URL、密钥或候选详情。保留上游响应体里的真实model字段，不为展示逻辑名强行改写流式响应；逻辑名/实际目标通过日志与受控元数据关联。

### 9.3 缓存

当前缓存以客户端模型名与body为主要身份。逻辑名映射变化后不能复用旧目标答案。

第一版逻辑池请求暂不复用生成响应缓存，既有直连模型缓存保持不变。未来启用时，键至少纳入入站协议、逻辑池、有效revision、真实目标/端点、请求内容与必要的权限隔离维度；鉴权与选择先于缓存，不在两个网关层重复启用缓存。

## 10. 实时配置与一致性

配置持久化于 IFF_DATA_DIR/model_pools.yaml；不在models.d中生成假模型YAML，也不复制云密钥。

保存流程：校验→以写锁/CAS比较revision→临时文件+原子替换→原子发布不可变快照。并发编辑使用expected_revision，旧版本提交返回409；加载失败保留最后有效快照。

每个请求捕获一次snapshot，期间不混读两版候选列表。快照编译时把候选引用解析为**完整的不可变路由数据**：目标端点定义（URL、认证引用版本、协议端点指纹）、上游模型ID、验证证据状态及其依赖指纹，一并冻结。池revision是外部接口；内部一致性键 = 池配置内容 + 所引用Provider/端点定义版本 + 证据状态版本。Provider配置、认证或模型元数据独立变化时，相关池快照的内部一致性键失效并触发重编译（对照§5.1使证据转stale），不需要管理员改池文件也不会把旧端点的验证结论或故障冷却带进新快照。新请求看到新revision，不影响在途流。禁用/撤销目标需要阻止之后新请求使用，包括会话固定请求；已发出的上游请求不承诺远程撤回。

候选健康状态不是配置文件的另一写入者；配置revision变化时按目标端点指纹决定是否保留冷却状态，不把所有故障一概清零，也不把旧端点故障带给新端点。

初始化时只在显式启用且验证通过的池上提供路由；配置损坏需报告不可用，不能回退到任意模型。

## 11. 管理与发现接口（拟议）

- GET /admin/model-pools：定义、revision、OpenAI/Anthropic有效候选、校验问题。
- PUT /admin/model-pools：带expected_revision的原子更新。
- POST /admin/model-pools/validate：静态校验+可选端点探测；实际生成/付费测试需明确选择。
- GET /admin/model-pools/status：端点健康、冷却、最近选择和回退原因。
- POST /admin/model-pools/dry-run：给定池、协议和能力要求，返回选择/排除原因；不发真实生成、不切GPU、不消费预算。
- /v1/models可列启用逻辑名，但不把所有候选能力取并集后宣称逻辑池都支持。按协议分别给能力覆盖说明；未配置/无兼容候选不能被标为ready。

管理页只做“逻辑模型池”一处入口，不再建四套模型/Provider管理系统。既有Provider和本地模型页管理真实目标，池页做选择、排序、协议可用性、策略与诊断。

## 12. 错误契约

按入站协议生成相应错误信封，保留稳定IFF code，不用错误格式切换来代替协议转换。

- unknown_pool：404。
- no_compatible_target：400，明确协议/能力不满足；不无限重试。
- pool_disabled / no_ready_target / pool_unavailable：503，可恢复时给有依据的Retry-After。
- key无效/无池权限：401/403，按现有兼容策略明确区分；不尝试另一个模型绕过权限。
- 本地正在切换：not_ready/switching，不把它当端点永久故障；是否跨位置回退由显式策略决定。
- 截断：保留已提交响应的协议与HTTP状态，记录truncated，不事后伪造另一个状态码。

不要向客户端回显上游密钥、原始认证头或未脱敏Provider错误。

## 13. 代码边界与与当前实现的关系

建议新建独立 model_pool 模块，包含配置模型/registry、兼容性过滤、确定性选择、端点健康状态与attempt预算；不要把所有逻辑继续堆到handler.py。

OpenAI/Anthropic入口共用同一选择内核，但保留各自解析与响应契约。入站鉴权→槽位识别/目标授权→选择→传输的顺序必须统一；不能让现有按短名鉴权、提前缓存查找与Provider前缀解析先吞掉 iff/ 别名。

直接调用真实模型的路径保持兼容，不自动把旧模型名重定向到某池。若未来需要兼容旧名称，必须有独立、显式启用的alias迁移表，不能悄悄劫持现有真实模型名。

完整故障回退需要受控单次上游尝试、统一budget和响应提交边界；需在独立PR中精确声明允许变更的传输接口与测试，不授予全转发核心无限制重写权。

## 14. 分期交付与验收

### 前置：稳定性收口

完成GPU线程锁、switch/reconcile协调与既有UI补丁质量门。sleep/wake不进入此范围。逻辑池设计不意味着这些修复已经完成。

### P1：稳定逻辑名、热映射、双协议过滤

交付四个默认槽位与自定义池结构、结构化目标引用、管理员配置、revision、纯dry-run；每次请求只选一个同协议目标，不宣称已经具备请求失败后的自动回退。保留直连模型行为。

### P2：受控优先级故障回退

在PR-14最小边界获批后加入single-attempt、总budget、提交后不重放、熔断与恢复、attempt观测。目标优先实现用户的槽位内自动切换，不增加语义LLM路由。

### P3：多agent会话与精细策略

验证并增加会话固定、可迁移性约束、每槽位deadline/队列策略、权限/出站策略的完整管理体验。P1/P2不能以“P3以后做”为由允许不可迁移内容被自动跨Provider重放；未实现会话能力前采取拒绝迁移的保守策略。

### 可选P4：跨协议转换

只有存在明确的“单协议目标必须服务另一协议客户端”需求才启动。独立评估adapter/LiteLLM及其完整兼容矩阵，不作为固定端口或热映射的必要前提。

### 核心验收

1. 同端口的两种客户端均可请求同一逻辑名，后端只选兼容协议端点。
2. 只有OpenAI端点的目标不会误接Anthropic请求；双协议目标只使用对应端点。
3. 请求进行中改映射，新请求用新revision，旧请求不换目标；并发编辑不会丢更新。
4. 优先级/冷却/半开恢复可重复验证；同目标多槽位共用容量。
5. 实际上游尝试次数不超过总预算，超时含排队/退避；部分流已输出后绝不切换或重放。
6. tools/图像/结构化输出/签名历史/上下文边界不匹配时明确拒绝，不静默删字段或截断。
7. 池权限、目标权限、出站限制不被别名绕过；旧guest配置不会自动扩权。
8. 池热更新不命中旧目标缓存；默认关闭池生成缓存且不改变直连缓存。
9. 失败主目标被备用救回时，仍能查到全部attempt与费用归属。
10. 本地未ready不触发抢占或VL启动；所有生命周期调用只经既有统一入口。
11. 服务端测试、SDK双协议用例、SSE/工具往返集成测试均使用假上游；真实GPU与付费生成分别申请。

## 15. 需要用户最终确认的业务边界

建议默认采用以下范围：

- 同一端口、入站协议保持不变；优先同协议原生端点，不默认转换。
- 槽位内按优先级自动切换，但只使用显式候选；跨本地/云回退默认关闭，可逐池显式开启。
- 本地只选择ready目标，不为满足槽位请求自动抢占GPU；VL启动与使用限制不因池化解除。
- 新功能单独立项；涉及PR-14核心接口的最小变更另行明确授权。

这些是本方案的推荐默认值，不伪称用户已批准全部实现细节。本文经独立builder check后再提交用户审阅；不提交Git、不部署、不变更现役配置。
